# seqta-calendar v2 多用户架构设计

**公开域名：** `https://timetable.leoze.top`
**身份提供方：** Authentik
**数据库：** PostgreSQL
**部署平台：** Proxmox VE / Debian LXC
**支持客户端：**

* Apple Calendar
* Google Calendar
* Google Calendar Android App
* 其他支持远程 ICS 订阅的日历客户端

---

# 1. 目标

系统需要支持：

1. 多个独立用户。
2. 每个用户拥有独立课表、设备、同步记录和订阅链接。
3. 用户只能查看和管理自己的课表。
4. 用户之间不能读取、修改或覆盖彼此的数据。
5. Tampermonkey 可以在同一浏览器内切换绑定用户。
6. 管理员可以创建、停用和管理用户。
7. 管理员可以允许或禁止用户同步。
8. 管理员可以允许或禁止日历订阅。
9. 管理员可以查看用户的课表和同步记录。
10. 普通用户不能进入 `/admin`。
11. 普通用户不能取得数据库、服务器、后台管理或其他用户权限。
12. Apple Calendar 和 Google Calendar 使用相同的 ICS Feed。
13. 保留当前 Apple Calendar 的订阅 URL 和事件 UID，避免重新产生重复事件。

# 2. Google Calendar 兼容方式

Google Calendar 可以直接订阅现有 ICS Feed，不需要 Google Calendar API。

使用流程：

```text
用户登录 timetable.leoze.top
        ↓
复制自己的 Calendar URL
        ↓
在电脑浏览器打开 Google Calendar
        ↓
Other calendars
        ↓
From URL
        ↓
粘贴 HTTPS ICS URL
        ↓
Google Calendar Android App 自动显示
```

Google 官方支持在桌面版 Google Calendar 中通过 URL 添加已发布日历。订阅完成后，该日历会出现在用户 Google Account 下；Android App 需要启用对应日历的 Sync。

Google Calendar Android App 本身不提供可靠的“直接输入 ICS URL”流程，因此网页中必须明确提示用户先在电脑网页版 Google Calendar 添加。

同一个 Feed：

```text
https://timetable.leoze.top/calendar/<secret>.ics
```

可以同时被：

```text
Apple Calendar
Google Calendar
Outlook
Thunderbird
```

订阅。

## 2.1 Google Calendar 刷新限制

Tampermonkey 同步后：

```text
SEQTA → 后端
```

会立即完成，但：

```text
后端 → Google Calendar
```

的刷新时间由 Google 控制。

后端不能命令 Google Calendar 立即重新抓取 ICS，也不能把网页中的“Sync Now”描述为“立即更新 Google Calendar”。

界面应显示：

```text
Backend updated successfully.

Apple Calendar and Google Calendar may take additional
time to refresh their subscribed copy.
```

## 2.2 ICS 输出要求

继续使用：

```http
Content-Type: text/calendar; charset=utf-8
Cache-Control: private, no-cache, max-age=0, must-revalidate
ETag: "calendar-<revision>"
Last-Modified: ...
```

每个事件保持：

```ics
UID:<永久稳定值>
SEQUENCE:<内容修改时增加>
DTSTAMP:<事件最后修改时间>
LAST-MODIFIED:<事件最后修改时间>
```

RFC 5545 使用稳定 `UID` 标识同一个事件，事件发生修改时使用 `SEQUENCE` 表示修订。UID 不应包含用户名、邮箱、学生编号等敏感信息。

# 4. 为什么从 SQLite 改成 PostgreSQL

SQLite 可以做多用户应用，但它没有原生 Row-Level Security。

在当前项目只有一个用户时，应用代码遗漏一次 `WHERE feed_id = ?` 的影响有限。多用户后，一次遗漏就可能把所有学生的课表返回给某个普通用户。

PostgreSQL Row-Level Security 可以在数据库层限制每个请求只能访问指定用户的数据。启用 RLS 后，没有匹配策略的访问默认拒绝。

新的安全结构必须是：

```text
HTTP authorization
        +
Repository ownership filtering
        +
PostgreSQL RLS
        +
Unique constraints
```

不能只依靠前端隐藏按钮，也不能只依靠 API 路由名称。

推荐使用：

```text
PostgreSQL 18
```

但代码不应依赖 PostgreSQL 18 独占功能，保持 PostgreSQL 17 兼容。

# 5. 用户角色

系统只设置三种角色：

```text
owner
admin
user
```

## 5.1 owner

你的账号。

权限：

* 访问 `/admin`
* 创建邀请
* 查看所有用户
* 查看所有课表
* 启用或停用用户
* 启用或停用同步
* 启用或停用 Calendar Feed
* 撤销设备
* 重置来源身份
* 轮换 Calendar Token
* 查看审计日志
* 管理其他管理员

## 5.2 admin

可选角色。

权限可以比 owner 少：

* 查看用户
* 查看课表
* 管理同步状态
* 撤销设备
* 不允许管理 owner
* 不允许提升其他用户为管理员
* 不允许修改系统设置

第一版可以完全不开放 `admin`，只有一个 `owner`。

## 5.3 user

普通同学。

只能：

* 查看自己的课表
* 查看自己的同步历史
* 创建自己的配对码
* 管理自己的 Tampermonkey 设备
* 复制自己的 Calendar URL
* 轮换自己的 Calendar URL
* 修改自己的日历显示名称
* 注销自己的网页会话

不能：

* 列出其他用户
* 查询其他用户 ID
* 读取其他日历
* 查看其他设备
* 调用管理 API
* 创建用户
* 修改自己的角色
* 修改 `sync_enabled`
* 修改 `feed_enabled`
* 访问数据库或服务器管理功能

# 6. Authentik 身份认证

使用 Authentik 作为 OIDC Provider。

Authentik OIDC 可以向应用提供：

```text
sub
name
preferred_username
email
groups
```

Authentik 的 `profile` scope 可以包含用户名、姓名和组成员信息，也可以通过 Property Mapping 增加自定义 Claims。

## 6.1 Authentik Groups

创建：

```text
seqta-calendar-users
seqta-calendar-admins
seqta-calendar-owners
```

层级：

```text
seqta-calendar-users
├── seqta-calendar-admins
│   └── seqta-calendar-owners
```

Authentik 的子组成员可以被视为父组的有效成员，因此管理员仍然可以访问普通用户应用。

## 6.2 OIDC 配置

```text
Application:
SEQTA Calendar

Provider:
OAuth2/OpenID Connect

Client type:
Confidential

Redirect URI:
https://timetable.leoze.top/auth/oidc/callback

Post logout redirect:
https://timetable.leoze.top/

Scopes:
openid
profile
email
```

## 6.3 本地用户绑定

应用必须使用：

```text
issuer + sub
```

作为外部身份唯一键。

不能使用：

```text
email
username
display_name
```

作为永久身份键。

数据库：

```text
oidc_issuer
oidc_subject
```

组成唯一约束。

用户改名或更换邮箱时不会创建第二个本地账号。

## 6.4 双重管理员判断

管理员访问必须同时满足：

```text
Authentik group 包含 seqta-calendar-owners
                    AND
数据库 users.role = owner
```

不能只相信前端传入的角色，也不能只看一个可修改的 URL 参数。

# 7. 用户邀请和注册

不开放公共注册。

## 7.1 邀请流程

```text
管理员在 /admin 创建邀请
        ↓
后端生成一次性邀请 URL
        ↓
管理员发给同学
        ↓
同学打开邀请
        ↓
通过 Authentik 登录
        ↓
后端将邀请绑定到 OIDC subject
        ↓
创建本地用户和空日历
```

邀请链接：

```text
https://timetable.leoze.top/invite/<256-bit-secret>
```

## 7.2 邀请属性

管理员可设置：

```text
显示名称
有效期
是否允许同步
是否允许 Calendar Feed
邀请备注
最大设备数量
```

默认值：

```text
角色：user
sync_enabled：true
feed_enabled：true
最大设备：3
有效期：72 小时
```

## 7.3 邀请安全

邀请 Token：

* 至少 32 字节随机值；
* 数据库只保存 HMAC Hash；
* 一次使用后立即失效；
* 不能重复绑定；
* 过期后不可使用；
* 不通过用户名或邮箱猜测邀请。

# 9. 权限状态

不要用一个 `enabled` 字段控制所有功能。

用户至少需要以下独立状态：

```text
account_status
sync_enabled
feed_enabled
```

## 9.1 account_status

```text
active
suspended
deleted
```

### active

正常登录和使用。

### suspended

* 不能登录用户 Portal；
* Device Token 不能同步；
* Calendar Feed 默认停止；
* 数据暂时保留；
* 管理员仍然可以查看。

### deleted

* 用户不可恢复使用；
* 所有 Device Token 失效；
* Calendar Token 失效；
* 数据进入删除保留期；
* 审计日志保留。

## 9.2 sync_enabled

管理员控制用户是否可以上传新课表。

关闭后：

```http
POST /api/device/sync
403 Forbidden
```

但现有 Calendar Feed仍可以继续显示最后一次课表。

适用于：

* 用户违规；
* 同步数据异常；
* 暂时冻结更新；
* 调试。

## 9.3 feed_enabled

管理员控制 Apple/Google Calendar 是否还能读取 Feed。

关闭后：

```http
GET /calendar/<token>.ics
410 Gone
```

返回：

```text
Calendar subscription disabled by administrator.
```

不建议返回空 ICS，因为客户端可能把所有事件解释为已删除。

# 10. Tampermonkey 设备配对

不能继续让管理员手动把永久 Upload Token 发给每个同学。

改用一次性配对码。

## 10.1 配对流程

```text
用户登录 /app/devices
        ↓
点击 Add browser
        ↓
生成 8 位一次性配对码
        ↓
用户在 Tampermonkey 面板输入配对码
        ↓
脚本请求 /api/device/pair
        ↓
后端返回 Device Token
        ↓
脚本保存 Device Token
```

配对码：

```text
7K4P-92MX
```

属性：

```text
有效期：10 分钟
只能使用一次
绑定当前用户
绑定一个 Calendar
```

## 10.2 Device Token

格式：

```text
dvc_<43-character-base64url>
```

Device Token 只能：

```text
POST /api/device/sync
GET  /api/device/status
```

不能：

```text
读取课表
读取 Calendar URL
列出其他用户
调用 /api/me
调用 /api/admin
修改账号
```

即使同学从 Tampermonkey 中复制了自己的 Device Token，也只能向自己的日历上传课表。

## 10.3 设备表

每个用户可以看到：

```text
Chrome on MacBook
Last active
Last sync
Created
Token prefix
Status
```

用户和管理员都可以撤销设备。

撤销后：

```text
Device Token 立即失效
现有 Calendar Feed 不受影响
```

```json
      "name": "Classmate",

      "calendarLabel": "Classmate Timetable"

```

```text

```

# 12. 防止把 A 的课表同步到 B 的账号

只有 Device Token 隔离还不够。

如果同一电脑登录了学生 A 的 SEQTA，但 Tampermonkey 选择了学生 B 的 Profile，A 的课表可能覆盖 B 的日历。

因此每个 Calendar 必须绑定一个不可随意改变的来源身份。

## 12.1 Source Identity

```text
school_host
seqta_student_ref
person_uuid_hash
```

首次成功同步时：

```text
source identity 未绑定
        ↓
锁定当前 school_host + student identity
```

以后所有同步必须匹配。

不匹配时：

```http
409 Conflict
```

```json
{
  "error": {
    "code": "SOURCE_IDENTITY_MISMATCH",
    "message": "This device is paired with a different SEQTA student."
  }
}
```

Tampermonkey 应显示：

```text
Sync blocked.

SEQTA currently shows student 4284, but this profile is
bound to another student. Switch profile or sign in to
the correct SEQTA account.
```

## 12.2 重置身份

普通用户不能自行重置。

只有管理员可以在：

```text
/admin/users/:id
```

执行：

```text
Reset source identity
```

重置前必须：

* 再次确认；
* 输入用户显示名称；
* 写入审计日志；
* 撤销现有 Device Token，或要求重新配对。

# 13. 数据库设计

## 13.1 users

```sql
CREATE TABLE users (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),

    oidc_issuer         text NOT NULL,
    oidc_subject        text NOT NULL,

    display_name        text NOT NULL,
    email               text,

    role                text NOT NULL DEFAULT 'user',
    account_status      text NOT NULL DEFAULT 'active',

    sync_enabled        boolean NOT NULL DEFAULT true,
    feed_enabled        boolean NOT NULL DEFAULT true,

    max_devices         integer NOT NULL DEFAULT 3,

    created_at          timestamptz NOT NULL DEFAULT now(),
    updated_at          timestamptz NOT NULL DEFAULT now(),
    suspended_at        timestamptz,
    deleted_at          timestamptz,

    UNIQUE (oidc_issuer, oidc_subject),

    CHECK (role IN ('owner', 'admin', 'user')),
    CHECK (account_status IN ('active', 'suspended', 'deleted'))
);
```

## 13.2 invitations

```sql
CREATE TABLE invitations (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    token_hash          bytea NOT NULL UNIQUE,

    created_by          uuid NOT NULL REFERENCES users(id),
    expected_name       text,
    note                text,

    sync_enabled        boolean NOT NULL DEFAULT true,
    feed_enabled        boolean NOT NULL DEFAULT true,
    max_devices         integer NOT NULL DEFAULT 3,

    expires_at          timestamptz NOT NULL,
    used_at             timestamptz,
    used_by             uuid REFERENCES users(id),

    created_at          timestamptz NOT NULL DEFAULT now()
);
```

## 13.3 calendars

```sql
CREATE TABLE calendars (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_user_id       uuid NOT NULL REFERENCES users(id),

    name                text NOT NULL,
    timezone            text NOT NULL DEFAULT 'Australia/Sydney',

    revision            bigint NOT NULL DEFAULT 0,
    last_synced_at      timestamptz,
    last_changed_at     timestamptz,

    created_at          timestamptz NOT NULL DEFAULT now(),
    updated_at          timestamptz NOT NULL DEFAULT now(),

    UNIQUE (owner_user_id)
);
```

第一版每个用户只有一个 Calendar。

保留独立 `calendars` 表，是为了将来支持：

* 多个学校；
* 多个学生；
* A/B 周课表；
* 单独考试日历。

## 13.4 source_identities

```sql
CREATE TABLE source_identities (
    calendar_id         uuid PRIMARY KEY REFERENCES calendars(id),

    school_host         text NOT NULL,
    student_ref         text NOT NULL,
    person_uuid_hash    bytea,

    locked_at           timestamptz NOT NULL DEFAULT now(),
    reset_at            timestamptz,
    reset_by            uuid REFERENCES users(id)
);
```

## 13.5 calendar_tokens

```sql
CREATE TABLE calendar_tokens (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    calendar_id         uuid NOT NULL REFERENCES calendars(id),

    token_hash          bytea NOT NULL UNIQUE,
    token_prefix        text NOT NULL,

    status              text NOT NULL DEFAULT 'active',

    created_at          timestamptz NOT NULL DEFAULT now(),
    last_used_at        timestamptz,
    revoked_at          timestamptz,

    CHECK (status IN ('active', 'revoked'))
);
```

只允许每个 Calendar 有一个活动 Token。

## 13.6 devices

```sql
CREATE TABLE devices (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_user_id       uuid NOT NULL REFERENCES users(id),
    calendar_id         uuid NOT NULL REFERENCES calendars(id),

    name                text NOT NULL,
    token_hash          bytea NOT NULL UNIQUE,
    token_prefix        text NOT NULL,

    status              text NOT NULL DEFAULT 'active',

    created_at          timestamptz NOT NULL DEFAULT now(),
    last_seen_at        timestamptz,
    last_synced_at      timestamptz,
    revoked_at          timestamptz,

    CHECK (status IN ('active', 'revoked'))
);
```

## 13.7 pairing_codes

```sql
CREATE TABLE pairing_codes (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_user_id       uuid NOT NULL REFERENCES users(id),
    calendar_id         uuid NOT NULL REFERENCES calendars(id),

    code_hash           bytea NOT NULL UNIQUE,
    expires_at          timestamptz NOT NULL,

    used_at             timestamptz,
```

# 14. PostgreSQL Row-Level Security

所有用户数据表启用：

```sql
ALTER TABLE calendars ENABLE ROW LEVEL SECURITY;
ALTER TABLE calendars FORCE ROW LEVEL SECURITY;

ALTER TABLE devices ENABLE ROW LEVEL SECURITY;
ALTER TABLE devices FORCE ROW LEVEL SECURITY;

ALTER TABLE events ENABLE ROW LEVEL SECURITY;
ALTER TABLE events FORCE ROW LEVEL SECURITY;

ALTER TABLE sync_runs ENABLE ROW LEVEL SECURITY;
ALTER TABLE sync_runs FORCE ROW LEVEL SECURITY;
```

用户请求进入事务后，应用设置：

```sql
SELECT set_config(
  'app.current_user_id',
  '<authenticated-user-uuid>',
  true
);
```

用户策略：

```sql
CREATE POLICY events_owner_policy
ON events
FOR ALL
USING (
    owner_user_id =
    current_setting('app.current_user_id', true)::uuid
)
WITH CHECK (
    owner_user_id =
    current_setting('app.current_user_id', true)::uuid
);
```

如果应用代码错误地执行：

```sql
SELECT * FROM events;
```

数据库仍然只返回当前用户自己的事件。

PostgreSQL RLS 在没有适用策略时采用 default-deny；同时必须注意表所有者通常会绕过 RLS，因此运行时数据库角色不能成为表所有者，并应使用 `FORCE ROW LEVEL SECURITY`。

## 14.1 数据库角色

```text
seqta_owner
seqta_migrator
seqta_user_api
seqta_device_api
seqta_admin_api
seqta_backup
```

### seqta_owner

* 拥有 Schema；
* `NOLOGIN`；
* 应用运行时不能使用。

### seqta_migrator

* 仅部署时使用；
* 可以执行 migrations；
* 不保存到普通运行环境。

### seqta_user_api

* 用户 Portal 请求；
* 受 RLS 限制；
* 不能访问管理表。

### seqta_device_api

* 只能调用同步所需 SQL；
* 不能任意读取事件；
* 不能读取 Calendar Token。

### seqta_admin_api

* 仅管理员路由使用；
* 应用必须先完成双重管理员认证；
* 所有操作写入 audit log。

### seqta_backup

* 仅备份服务使用；
* 不能用于 Web Application。

# 17. Cloudflare 路由和 Access

Cloudflare Tunnel 继续发布：

```text
timetable.leoze.top
→ http://127.0.0.1:3210
```

Cloudflare Tunnel 可以将公开 hostname 映射到本地服务，且 Cloudflare 可在转发至 origin 前应用 WAF、Access 和其他策略。

## 17.1 路径分类

| 路径              | Cloudflare Access |                   应用认证 |
| --------------- | ----------------: | ---------------------: |
| `/calendar/*`   |                 否 |         Calendar Token |
| `/api/device/*` |                 否 |           Device Token |
| `/app/*`        |                 否 | Authentik OIDC Session |
| `/api/me/*`     |                 否 | Authentik OIDC Session |
| `/admin/*`      |                 是 |    Owner/Admin Session |
| `/api/admin/*`  |                 是 |    Owner/Admin Session |
| `/health/*`     |                 否 |                  无敏感数据 |

Cloudflare Access 支持针对指定 hostname 路径单独建立 Access Application，因此可以只保护 `/admin/*` 和 `/api/admin/*`。

## 17.2 Admin 双层保护

访问 `/admin` 必须通过：

```text
Cloudflare Access
        +
Authentik OIDC
        +
本地 owner/admin role
```

Cloudflare Access Policy：

```text
Include:
Leo 的指定邮箱或 Authentik owner group

Require:
MFA
```

即使 Cloudflare Access 配置失误，应用仍必须拒绝普通用户。

## 17.3 Calendar Feed 不能放在 Access 后

Apple Calendar 和 Google Calendar 无法完成 Cloudflare Access 的交互式登录。

因此：

```text
/calendar/<256-bit-token>.ics
```

必须公开可请求，但依靠不可预测 Token 授权。

Calendar URL 泄露等于课表泄露，所以必须支持：

* 用户自行轮换；
* 管理员轮换；
* 立即撤销；
* 日志中脱敏；
* 页面默认隐藏；
* 点击后才显示；
* 不发送给第三方分析工具。

# 20. 现有系统迁移

必须保留你当前的：

* Calendar Token；
* Feed URL；
* Event UID；
* Event `SEQUENCE`；
* 当前 Apple Calendar 订阅。

否则 Apple Calendar 可能把所有课程视为新事件。

## 20.1 迁移步骤

```text
1. 停止旧后端同步写入
2. 完整备份 SQLite 和 Secrets
3. 部署 PostgreSQL
4. 创建你的 Authentik owner 账号
5. 创建 users 记录
6. 创建你的 calendars 记录
7. 导入现有 events
8. 为所有事件写入 owner_user_id
9. 保留原 ical_uid
10. 保留 sequence
11. 导入原 Calendar Token Hash
12. 导入 source identity
13. 验证旧 URL 输出内容一致
14. 启用 PostgreSQL RLS
15. 部署用户 Portal
16. 部署 Admin Portal
17. 升级 Tampermonkey 为配对模式
18. 开始邀请同学
```

## 20.2 不允许改变

迁移时不能重新计算：

```text
ical_uid
calendar token
natural_key
```

除非当前数据本身有冲突。

## 20.3 验证方法

迁移前后分别保存：

```text
before.ics
after.ics
```

允许变化：

```text
PRODID
非语义属性顺序
服务器响应头
```

不允许变化：

```text
UID
DTSTART
DTEND
SUMMARY
```

# 23. 最终安全边界

```text
同学的网页 Session
只能访问 /api/me/*
        ↓
只能映射到自己的 user_id
        ↓
只能使用 seqta_user_api 数据库角色
        ↓
PostgreSQL RLS 再次限制 owner_user_id
```

```text
同学的 Device Token
只能访问 /api/device/*
        ↓
只能绑定一个 calendar_id
        ↓
只能上传
不能读取
不能管理
```

```text
Calendar Token
只能读取一个 Calendar Feed
不能同步
不能登录
不能调用 API
```

```text
Owner
Cloudflare Access
        +
Authentik owner group
        +
本地 owner role
        +
Admin API authorization
        +
审计日志
```

这套结构下，同学不是“拥有一个后端账号”，而是只拥有三个严格分离的能力：

```text
网页登录自己的 Portal
设备上传自己的课表
日历客户端读取自己的 Feed
```

任何一个 Token 泄露，都不会自动得到另外两种权限。
